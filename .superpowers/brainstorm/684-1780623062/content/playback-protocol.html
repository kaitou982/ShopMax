观众端播放协议

不同协议在延迟、兼容性、实现复杂度上有显著差异

A

HTTP-FLV（推荐）

延迟：1~3 秒  |  库：mpegts.js

特点

  • 低延迟，适合实时互动场景
  • 基于 HTTP，穿透性好（CDN/防火墙友好）
  • mpegts.js 成熟稳定，API 简洁
  • SRS 原生支持 HTTP-FLV 流

劣势

  • iOS Safari 不原生支持 FLV（需要 mpegts.js 软解码）
  • 大码率时 CPU 占用较高
B

HLS

延迟：5~30 秒  |  库：hls.js

特点

  • 兼容性最好，所有浏览器/设备原生支持
  • CDN 分发成熟，适合大规模观众
  • 苹果生态友好（Safari 原生 HLS）

劣势

  • 延迟高（切片机制导致 5~30 秒延迟）
  • 不适合需要实时互动的直播场景
  • 切片文件占用存储空间
C

WebSocket-FLV

延迟：1~3 秒  |  库：mpegts.js (ws://)

特点

  • 低延迟，通过 WebSocket 传输 FLV 数据
  • 穿透性强，不受 HTTP 代理限制
  • 可复用已有的 WebSocket 基础设施

劣势

  • WebSocket 连接数有上限
  • 不适合大规模观众（需配合 CDN）
  • SRS 的 WebSocket-FLV 配置略复杂
D

自适应切换（推荐组合）

Web 端：HTTP-FLV 优先，HLS 兜底  |  移动端：HLS 优先

策略

  • Web 端用 mpegts.js 播放 HTTP-FLV（低延迟）
  • Web 端如果 mpegts.js 加载失败，降级到 HLS
  • 移动端 UniApp 用 HLS（兼容性最好）
  • 微信小程序用 HLS（小程序原生支持）

优势

  • 兼顾延迟和兼容性
  • 覆盖所有平台（Web/H5/小程序/App）

劣势

  • 实现稍复杂，需要播放器适配层

我的建议

选 D（自适应切换）。ShopMax 是三端项目（Web + H5 + 小程序），不同平台最优协议不同：

  • Web 端：HTTP-FLV 延迟低，互动体验好
  • 移动端/H5：HLS 兼容性最好
  • 微信小程序：只支持 HLS

SRS 同时输出 HTTP-FLV 和 HLS，无需额外配置。
