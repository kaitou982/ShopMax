## 二、项目介绍(ShopMax)—— 重点讲真实技术

> 面试官大概率说:"挑一个项目详细讲讲。" 先用 2.1 总述 1 分钟,然后观察反应:如果他问架构就讲 2.2,如果问"最有成就感的模块"就从 2.3 挑 1-2 个讲。**原则:只讲自己讲得清原理的部分,宁深勿广。**

### 2.1 一分钟总述模板

> ShopMax 是一个 B2C 商城 + 直播带货 + 社交内容社区的全栈电商平台,后端 Java 21 + Spring Boot 3.2 + Spring Cloud Alibaba,前端 Vue 3 + TypeScript + UniApp。
>
> 后端按业务域拆成 12 个服务:网关、认证两个基础设施,加用户、商品、订单、支付、营销、直播、社区、客服、文件、管理后台十个业务服务;用 Nacos 做注册和配置中心,OpenFeign 做服务间调用,每个调用都配了 FallbackFactory 降级。核心业务包括:Redis Lua 脚本实现的秒杀、JWT 双 Token 认证、支付宝沙箱支付与退款、WebSocket 直播弹幕送礼、MiMo 大模型的 AI 客服。
>
> 前端是 pnpm Monorepo:PC 端、移动端、管理后台三端,共享 API 客户端和 TypeScript 类型。部署上用了 Docker 多阶段构建 + GitHub Actions,推代码自动构建、SSH 部署到阿里云 2 核 4G 服务器,前端部署在 Vercel。整个项目从数据库设计到上线监控全链路都是我一个人完成的。

### 2.2 架构讲解(带真实数字,口述版)

**后端分层**(讲给技术面试官):

- **12 个服务** = 2 基础设施(gateway 网关、auth 认证)+ 10 业务(user 用户、product 商品、order 订单、payment 支付、marketing 营销、live 直播、community 社区、admin 管理、customer 客服、file 文件);
- **Gateway 网关**:11 条服务路由 + 2 条 WebSocket 路由,4 个全局过滤器——AuthGlobalFilter(JWT 认证 + 黑名单校验)、RateLimitFilter(限流)、TraceFilter(生成 X-Trace-Id 链路 ID)、GrayReleaseFilter(灰度发布);
- **服务治理**:Nacos 注册/配置中心,Feign 声明式调用,每个 FeignClient 都有 FallbackFactory 降级工厂,内部接口统一 `/internal/` 前缀(不经过网关认证,服务间直连);Sentinel 熔断,规则是慢调用比例 500ms/50% 触发、异常比例 50%,熔断 30 秒;
- **一致性**:下单用 Seata AT 模式 `@GlobalTransactional` 保证订单-库存-支付数据一致性;RocketMQ 订单 topic 异步解耦;秒杀场景则用**本地消息表 + 定时任务**替代 MQ(下面讲为什么)。

**前端三端**:

- `shop-frontend/` 是 pnpm workspace monorepo,三个包:`@shop/web`(PC 端,Vite + Vue 3 + **Naive UI**)、`@shop/mobile`(UniApp 跨端,34 个页面 + uni-ui)、`@shop/shared`(共享层:12 个模块的 API 客户端、Pinia store、类型定义);
- 共享层做了 **HttpClient 抽象**:定义统一接口,PC 端用 axios 实现、移动端用 uni.request 实现,业务代码不关心平台差异;
- `shop-admin-ui/` 管理后台独立工程,**Element Plus** + 自定义 `v-permission` 权限指令(按角色控制按钮/菜单显隐);
- 全工程 TypeScript strict 模式,组件 Props/Emits 全部类型化。

**部署与可观测性**:

- Docker 多阶段构建:构建阶段先 COPY pom.xml + `dependency:go-offline` 预下载依赖(利用层缓存),再 COPY 源码;运行阶段用 `eclipse-temurin:21-jre-alpine`,G1GC + `MaxRAMPercentage=75%`,单服务内存 192-256MB;
- 生产环境是阿里云 **2 核 4G** ECS,全套 12 服务 + 10 个中间件要 4.5GB+ 内存跑不动,所以生产精简为 **5 个核心微服务**(gateway/user/product/community/auth)+ Nginx/MySQL/Redis/Nacos/MinIO,每个容器都有限制内存和健康检查,整机内存 2.8GB/4GB,利用率 70%;
- GitHub Actions:push 触发三路并行构建(后端 Maven + 前端 Web/Admin),main 分支 SSH 到 VPS 执行 `docker compose up -d --build` 滚动更新,前端 Vercel 自动部署;
- 可观测性:Micrometer Tracing + Brave 做全链路追踪(X-Trace-Id 从网关注入,经 Feign 拦截器跨服务传播,日志格式统一带 traceId);所有服务暴露 `/actuator/prometheus` 给 Prometheus 采集,Grafana 出大盘;ELK 收日志;XXL-JOB 跑 5 个定时任务(超时订单关闭、秒杀消息重试、库存同步、团购过期处理等)。

### 2.3 核心模块深挖版(被问"挑一个最有成就感的模块"时讲)

#### 2.3.1 高并发秒杀(最推荐讲的模块,完整链路)

> 秒杀最核心的问题是两件事:**防超卖**和**削峰**。
>
> 防超卖我做了三层保障:第一层,库存放在 Redis,扣减用 **Lua 脚本**一次原子完成——脚本里做四件事:查用户是否已买过(一人一单)、查库存是否充足、扣减库存、记录购买用户,整段脚本在 Redis 里单线程执行,不会出现"两个请求同时查到有库存都下单"的竞态;第二层,数据库层用**乐观锁**,UPDATE 语句带 `WHERE seckill_stock > 0` 条件,即使 Redis 出问题数据库也不会扣成负数;第三层,秒杀入口还有 Redis 分布式锁做单用户串行化。
>
> 削峰我用的是**本地消息表**方案:抢到库存后不直接建单,而是往 `mms_seckill_message` 表写一条消息,由定时任务异步扫描消息表去建订单。重试用了指数退避——重试间隔 = 重试次数 × 5 分钟,避免失败请求密集轰炸数据库。订单创建后 15 分钟未支付会超时关闭、回滚库存,再定时把 Redis 里的库存同步回数据库做最终兜底。
>
> 为什么不用 RocketMQ 而是本地消息表?因为生产服务器只有 2 核 4G,跑不起完整的 RocketMQ(需要 NameServer + Broker),本地消息表用一张表 + 定时任务就能达到同样目的,这是资源和需求权衡的结果——这个决策过程是我从这个模块学到的最有价值的东西。

**可能会被追问的点(提前想好)**:
- "Lua 为什么是原子的?" → Redis 单线程执行脚本,整个脚本执行期间不会被其他命令插入;
- "乐观锁和 Lua 不是重复吗?" → 双保险:Redis 是性能层,DB 乐观锁是数据一致性兜底,极端情况下(Redis 与 DB 数据不一致)保证不超卖;
- "超卖到底什么场景会发生?" → 典型的 check-then-act 竞态:两个并发请求都读到 stock=1,都通过判断,都执行扣减;
- "消息表重试会不会重复建单?" → 每条消息有状态字段(PENDING/SUCCESS/FAILED)+ 幂等校验(按用户+场次查已购记录)。

#### 2.3.2 认证与安全

> 登录认证我做的是**双 Token 机制**:Access Token 有效期 1 天,Refresh Token 7 天。Access 过期后用户用 Refresh 换新的,换的时候旧 Refresh Token 会加入 Redis 黑名单(Key 是 `token:blacklist:{token}`)——这叫轮换,目的是即使 Refresh Token 被泄露,用过一次立刻失效。网关的 AuthGlobalFilter 和业务侧的 JwtAuthenticationFilter 都会检查黑名单,防止已登出的 Token 重放。
>
> 另外做了登录防爆破:同一用户名连续失败 5 次锁定 30 分钟,Key 用 `login:fail:{username}` 记录失败次数,到 5 次就设置过期时间 30 分钟。权限上是 RBAC 三角色——ADMIN(管理员)、STORE(商家)、USER(普通用户),管理端接口用 `@PreAuthorize("hasRole('ADMIN')")` 这类注解做方法级权限控制。

#### 2.3.3 支付与退款

> 支付对接的是**支付宝沙箱环境**,用的官方 SDK `DefaultAlipayClient`,支持电脑网页、手机网页、扫码三种方式。核心做了两件事:一是**防重复支付**——创建支付单前先查有没有已存在且成功的支付单,有就直接返回,支付回调也做幂等;二是**回调验签**——用 `AlipaySignature.rsaCheckV1` 校验支付宝回调的 RSA 签名,防止伪造回调。退款支持全额和部分退款,部分退款会校验退款金额不超过已付金额,退款单号幂等。

#### 2.3.4 AI 客服(Tool Calling,投 AI 方向必讲)

> AI 客服对接的是 MiMo 大模型 API(模型 `mimo-v2-flash`,Java 21 的 `java.net.http.HttpClient` 调用)。关键是 **Tool Calling 机制**:模型不会直接回答"我的订单到哪了",而是返回一个 `tool_calls` 指令,我的代码解析这个指令,调用对应的后端工具——我定义了四个工具:查商品、查订单、搜 FAQ、推荐商品——拿到真实结果后再把结果回传给模型,让模型基于真实数据组织回答。这个过程是多轮循环的:模型调工具 → 工具返回 → 模型再决定继续调工具还是出最终答案。这样做的意义是**让大模型接入真实业务数据,而不是让它编造**。

#### 2.3.5 直播互动

> 直播模块的实时交互用 WebSocket 长连接实现。服务端有一个统一的消息处理器,按消息类型分发处理三种消息:弹幕(直接广播给房间内所有人)、点赞(用 Redis 计数器 `live:like:` 累加,定时批量落库,避免高频写数据库)、送礼(走礼物服务,涉及扣余额、加主播收益)。推流用的是 SRS 流媒体服务器,推流端鉴权是 SRS 的回调接口,校验推流密钥和 JWT 才允许开播。前端用 hls.js/mpegts.js 拉流播放。

#### 2.3.6 前端工程化

> 前端我比较自豪的是工程化规范。Monorepo 三端共享 `@shop/shared` 包:API 客户端按 12 个业务模块封装,类型定义、Pinia store(用户、购物车)全部共享,一套代码三端复用。HTTP 层做了平台抽象:定义 HttpClient 接口,PC 端注入 axios 实现,移动端注入 uni.request 实现,统一处理 Token 注入、401 跳登录、错误提示。管理后台做了 `v-permission` 自定义指令,按钮级权限控制。全工程 TS strict,没有 any,组件 Props/Emits 全类型化。

### 2.5 最大困难与解决(必问题,准备两例)

**例 1:2 核 4G 服务器跑不动全套架构(推荐讲,体现工程判断)**

> 我遇到的比较大的困难是:开发环境里 12 个服务加全套中间件跑得好好的,部署到 2 核 4G 的服务器上内存直接爆了——光中间件就要 4.5GB。我做的取舍是:生产环境只保留 5 个核心服务(网关、认证、用户、商品、社区),砍掉 ES、Kibana、RocketMQ、Seata、Sentinel 控制台这些重型组件;秒杀异步建单从 MQ 改成本地消息表;给每个容器精确设置内存限制和健康检查,JVM 用 G1GC 和容器感知参数,最后把整机内存压到 2.8GB,利用率 70%。
> 这件事让我认识到:技术选型不是越全越好,而是要和资源、需求匹配。微服务的成本(运维复杂度、分布式一致性问题)是真实的,什么时候该上、什么时候该砍,这种判断力比会用组件更重要。

**例 2:秒杀超卖问题(讲排查思路)**

> 做秒杀第一版的时候,我用的是"先查库存再扣减"的两步操作,自己测试没问题,但我意识到并发下会有竞态——两个请求同时查到库存是 1,就都下单了。后来我把扣库存逻辑改成 Redis Lua 脚本原子执行,再在数据库层加乐观锁兜底。这个问题的价值不在解决方案本身,而在于我开始习惯性地问自己"这段代码并发执行会不会出错"。

### 2.6 主动谈项目的不足(面试官问"有什么可以改进的"时)

### 3.3 技术快速问答(HR 面或技术面都可能问)

**Q19. 用大白话讲一下你项目的架构?(讲给不懂技术的 HR 听)**
> 我把它想象成一个商场:网关是商场大门(统一入口、安检),Nacos 是导览系统(知道每家店在哪),12 个服务是不同店铺(卖东西的、管会员的、管直播的各司其职),MySQL 是仓库,Redis 是收银台旁边的临时柜台(放最热的数据,秒杀库存就放这),消息队列/消息表是排队叫号系统(高峰期不挤爆收银台)。所有店铺的服务状态、日志、监控都有统一系统盯着,出问题能快速定位是哪家店。

**Q20. 秒杀用 Redis Lua,为什么 Lua 能保证不超卖?**
> Redis 执行 Lua 脚本是单线程原子的:整段脚本执行期间不会插入其他命令。我把"查库存 → 判断够不够 → 扣减"压缩在同一个脚本里,并发再高也是排队执行,不会出现两个请求同时看到"库存 1"的情况。数据库层我还加了乐观锁 UPDATE 带 stock>0 条件,双保险。

**Q21. 双 Token 有什么用?Access 过期了怎么办?**
> Access Token 短(1 天)是为了泄露后损失小;Refresh Token 长(7 天)是为了用户不用频繁登录。Access 过期后用 Refresh 换新,换的同时旧 Refresh 进黑名单作废(轮换)。安全性提升在:攻击者偷到 Refresh 也只能用一次。⚠️ 前端目前是 401 统一跳登录,没有静默刷新——这是我的待办项,如实说。

**Q22. 本地消息表是什么?为什么不直接用 RocketMQ?**
> 本地消息表是 MQ 的简化替代:业务操作和"待办消息"写在同一张表里(同一个数据库事务,天然一致),然后定时任务扫表处理,失败按指数退避重试。好处是不依赖额外中间件、事务简单;代价是吞吐不如真 MQ。我用它是因为生产服务器资源有限,这是权衡;开发环境里 RocketMQ 也跑过,订单创建后发 order-topic 异步解耦。

**Q23. 你做过压测吗?秒杀能扛多少并发?**
【意图】戳破数字泡沫。
> 我没有做过严格的大规模压测,所以我不报具体数字——报了也是假的。我做过的验证是:双实例负载均衡验证、Sentinel 限流验证、接口功能联调。如果入职后有压测需求,我会用 JMeter 补上,这正是我想在团队里学的。(⚠️ 千万不要编 QPS 数字,懂行的面试官追问脚本细节必露馅。)

**Q24. 全栈的话,前端和后端你更偏哪边?**
